# investigate — 系统性根因调试

> 来源：gstack-main/investigate/SKILL.md（精简移植）
> 核心：没有根因，不要修复。

## 铁律

**没有根因调查在前，就不要修复。**

修复症状造成打地鼠调试。
每一个没有解决根本原因的修复，都让下一个 bug 更难找。
找到根因，然后修复它。

---

## 阶段1：调查（Investigate）

收集上下文，在形成任何假设之前。

1. **收集症状：** 读错误信息、堆栈跟踪、重现步骤。
   如果用户提供的信息不够，通过 AskUserQuestion 一次只问一个问题。

2. **读代码：** 从症状回溯到可能的原因。
   用 Grep 找所有引用，读懂逻辑。

3. **检查最近的变更：**
   ```
   git log --oneline -20 -- <affected-files>
   ```
   之前能工作吗？什么变了？回归意味着根因在 diff 里。

4. **复现：** 能确定性触发 bug 吗？
   如果不能，收集更多证据再继续。

---

## 阶段2：分析（Analyze）

隔离变量：什么改变了？

```
- 什么改变了？
  - 代码变更（git blame）
  - 依赖版本变化
  - 环境变化
  - 数据变化
  
- 症状在哪里？
  - 在用户界面
  - 在日志里
  - 在监控里
  - 在某个特定条件下
```

---

## 阶段3：假设（Hypothesize）

提出可能的原因（至少2个），每个假设标注置信度：

```
假设 A: [描述]
  置信度: 80%
  验证方法: [设计验证实验]
  
假设 B: [描述]
  置信度: 20%
  验证方法: [设计验证实验]
```

设计验证实验——如何验证或排除每个假设？

---

## 阶段4：实施（Implement）

从置信度最高的假设开始：

```
1. 修复
2. 验证
3. 确认修复有效
4. 如果失败 → 返回阶段3修正假设
```

**关键：每一步都要验证，不要假设修复有效。**

---

## 追问模板

| 情况 | 追问 |
|------|------|
| 错误信息不明 | "完整的错误信息是什么？能提供堆栈跟踪吗？" |
| 无法复现 | "这个问题是在什么情况下出现的？每次还是偶发？" |
| 回归 | "这个功能上次能工作是什么时候？最后一次成功运行和第一次失败之间有什么变化？" |
| 假设太多 | "哪个假设能最快被验证或排除？" |

---

## 调试输出格式

```
症状：...
可能原因：
  - [假设A]（置信度X%，验证：...）
  - [假设B]（置信度X%，验证：...）
验证结果：...
根因：...
修复：...
```

---

## 完成状态协议

```
DONE：所有步骤完成，每条结论提供了证据
DONE_WITH_CONCERNS：完成，但有用户应知道的问题
BLOCKED：无法继续，说明阻塞原因和已尝试的方法
NEEDS_CONTEXT：缺少必要信息，说明具体需要什么
```

---

## 自改进（完成前必须做）

反思：
- 哪些命令意外失败？
- 是否走了弯路需要回退？
- 是否发现项目特定的坑？
- 什么比预期花了更长时间？

如有发现 → 记录到 evolver：
```
记录类型: operational
关键: [SHORT_KEY]
发现: [描述]
置信度: N/10
来源: observed
```
