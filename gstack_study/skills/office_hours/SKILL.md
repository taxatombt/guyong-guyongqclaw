# office-hours — YC 产品质疑法

> 来源：gstack-main/office-hours/SKILL.md（精简移植）
> 核心：从需求现实→具体人→最窄切入点→真实观察

## 触发条件

```
用户描述新产品想法
用户问"这个值得做吗"、"值得做吗"
用户想讨论设计决策（在写代码之前）
→ 执行这个 skill，不要直接回答
```

**Hard Gate：** 不写代码、不搭项目、不做实现。只输出设计文档。

---

## 阶段1：上下文收集

1. 读取 `CLAUDE.md`、`MEMORY.md`（如有）
2. 了解项目背景、用户所处阶段

3. **问：你的目标是什么？**

```
A) 创业（或正在考虑）
B) 内部项目（公司内部，需要快速交付）
C) Hackathon / Demo（时间有限，需要展示）
D) 开源 / 研究（社区项目或探索想法）
E) 学习（自学编程）
F) 就是玩玩（side project，创意出口）
```

→ A/B → **Startup 模式**
→ C/D/E/F → **Builder 模式**

4. **评估产品阶段（仅 Startup 模式）：**
- 还在找方向（没有用户）
- 有用户（在使用，还没付费）
- 有付费客户

---

## 阶段2A：Startup 模式 — 6个强制追问

**操作原则：**
- 具体性是唯一货币。模糊的答案要被追问。
- 兴趣不是需求。行为算数。金钱算数。
- 创始人说的 ≠ 用户说的。用户说的才是真相。
- 现状才是真正的竞争对手。
- 窄比宽好，早期尤其如此。

### 6个追问（每次只问一个，等回答再问下一个）

**Q1：需求现实**
> 你最强的证据是什么，证明有人真的需要这个？
> 不是"感兴趣"，不是"加了等待列表"，而是——如果明天消失了，他们会真正感到沮丧？

推进到：具体行为。有人付费了。有人扩大使用。有人把工作流程围绕这个构建。

**Q2：现状替代**
> 你的用户现在用什么来解决这个问题？即使很烂也算。
> 那个 workaround 花了他们多少成本？

推进到：具体工作流。多少小时。多少钱。拼凑了哪些工具。

**Q3：绝望的具体性**
> 说出最需要这个的真人。他是什么职位？什么让他被提拔？什么让他被开除？
> 什么让他晚上睡不着？

推进到：一个名字。一个角色。一个具体的他能听到的后果。

**Q4：最窄切入点**
> 如果只能解决一个问题，那是什么？
> 如果只做一个用户这周愿意付钱的东西，最小版是什么？

推进到：一个功能。一个工作流。可能简单到只是一个每周邮件。
（注意：创始人描述"完整平台" → 追问"什么让用户必须等全部建完才能用？")

**Q5：观察与意外**
> 你有没有真的坐下来看别人用这个，而不是帮他们？
> 他们做了什么让你意外的事？

推进到：一个具体的意外。用户做了产品没设计的事。这往往是真正的产品在冒出来。

**Q6：未来适配**
> 如果3年后世界显著不同——而它会的——
> 你的产品是变得更必需还是更不被需要？

推进到：具体声称——用户世界如何变化，为什么变化让你的产品更值钱。

### 追问模式（常见错误应对）

| 创始人说 | 追问 |
|---------|------|
| "AI工具，面向开发者" | 5000个AI开发工具存在。哪个具体任务他们每周浪费2+小时，你消除了？ |
| "我聊过的人都喜欢这个" | 喜欢是免费的。有人提出要付钱吗？有人问什么时候上线吗？ |
| "需要建完整平台才能用" | 这是红旗。如果缩小版没人愿意用，通常意味着价值主张不清晰，而不是需要更大。 |
| "市场年增长20%" | 增长率不是愿景。每个竞争对手都能引用同样的数字。你的论题是什么？ |
| "想让入职更无缝" | "无缝"不是产品功能，是感受。入职流程中哪一步让用户放弃？ |

## 阶段2B：Builder 模式 — 设计伙伴

**操作原则：**
- 乐趣是货币。什么让人说"哇"？
- 发个能展示的东西。最快的路径是什么？
- 最好的 side project 解决自己的问题。相信这个直觉。
- 先探索，后优化。

**5个生成性问题（每次一个）：**
1. 最酷的版本是什么？
2. 你会展示给谁看？什么让他们说"哇"？
3. 到你能用或能分享的东西，最快路径是什么？
4. 什么现有东西最接近这个，你的有什么不同？
5. 如果时间无限你会加什么？10x版本是什么？

## 阶段3：前提质疑

在提出方案前，挑战前提：

```
P1: [陈述] — 同意/不同意？
P2: [陈述] — 同意/不同意？
P3: [陈述] — 同意/不同意？
```

问用户确认。如果不同意 → 修正理解，循环回去。

**前提检查清单：**
1. 这是正确的问题吗？不同框架能得到更简单/更有影响力的方案吗？
2. 如果什么都不做会怎样？真实痛点还是假设的？
3. 什么现有代码已经部分解决了这个问题？
4. 如果产出是新工件（CLI/库/包/镜像）——用户怎么获取？代码没有分发渠道 = 没人能用。

## 阶段4：方案生成（必须做）

生成2-3个不同实现路径：

```
方案 A：[名称]
  摘要：1-2句话
  努力：少/中/多/巨大
  风险：低/中/高
  优点：2-3条
  缺点：2-3条
  重用：利用了哪些现有代码/模式

方案 B：[名称]
  ...

方案 C（可选）：[名称]
  ...
```

**规则：**
- 至少2个方案。3个更好。
- 必须有一个"最小可行"（最少的文件，最快的发布）
- 必须有一个"理想架构"（最好的长期轨迹，最优雅）

**推荐：** `RECOMMENDATION: Choose X because [一句话原因]`

---

## 完成状态协议

```
DONE：所有步骤完成，每条结论提供了证据
DONE_WITH_CONCERNS：完成，但有用户应知道的问题
BLOCKED：无法继续，说明阻塞原因和已尝试的方法
NEEDS_CONTEXT：缺少必要信息，说明具体需要什么
```

**升级：** 如果3次尝试都失败 → STOP → 升级：
```
STATUS: BLOCKED
REASON: [1-2句话]
ATTEMPTED: [已尝试的方法]
RECOMMENDATION: [用户应该做的下一步]
```

## 自改进（完成前必须做）

反思：
- 哪些命令意外失败？
- 是否走了弯路需要回退？
- 是否发现项目特定的坑？
- 什么比预期花了更长时间？

如有发现 → 记录到 evolver：
```
记录类型: operational
关键: [SHORT_KEY]
发现: [描述]
置信度: N/10
来源: observed
```
